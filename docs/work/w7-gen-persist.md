## 一、缺口是什么

W3 把生成链路接到编辑页时，生成结果是这样落库的：

```
任务成功
  → 编辑页 effect 把 video_url 写进草稿
  → useProjectEditor 置「未保存」
  → 2 秒防抖
  → repository.save
```

三个后果，按严重程度排：

1. **离页即丢结果。** 生成一板要好几秒，用户点完就走是常态。任务跑完那一刻编辑页
   已经卸载，effect 不会再跑，`video_url` 只留在内存的任务表（localStorage）里，
   项目里没有。回到列表页看到的是「未生成」，成片页也读不到地址。
2. **失败完全不落库。** 只有成功路径回写。离页再回来，失败的板显示「待生成」,
   用户不知道刚才那次生成已经失败过。
3. **结果被算成用户改动。** 回写走 `update()`，顶部栏跳成「未保存」，
   紧接着自动保存又跳回「已保存」——保存态无端抖一下，用户以为自己动了什么。

还有一条更隐蔽的：编辑态里的 `status` 是挂载那一刻的快照，编辑区从不改它。
生成后随便改一个字再保存，`withDrafts` 会把 `generated` 盖回 `filled`。

## 二、修法：挂点从组件订阅搬到状态机终态

```
任务进终态（SUCCEEDED / FAILED）
  → queue.onSettle                      ← 挂在状态机上，不是组件订阅上
  → generateResults.settle(job)
      读库 → applyJobResult 合进那一板 → repository.save
  → onPersisted
      → editor.patch(...)               ← 只对齐草稿，不置「未保存」
```

关键不在「写得更早」，而在**挂点的生命周期**。`onSettle` 在
`createGenerateQueue` 时接一次线，队列被在途的 `drain()` promise 持有，
因此它比编辑页活得久：`controller.dispose()` 只解绑视图订阅，落库通道不受影响。

为什么不是别的修法：

- **把防抖调短**：治不了离页，只是把窗口缩小。
- **在离页时 flush**：`useProjectEditor` 卸载时本来就 flush，但那时任务还没跑完，
  草稿里根本还没有结果可写。
- **让编辑页在 unmount 后继续订阅**：那是内存泄漏，而且换项目时会串。

编辑页仍留一个**补写** effect（`jobResultPending` → `settle`），管的是残留：
上次离页时写盘失败、或本地任务表比项目新（换机导入了旧项目）。正常路径不会进这里。

## 三、四个设计决策

### 1. 失败只落 `status`，不落 `prompt_final`

失败任务的 prompt 快照没有落库价值，而「内容违规」类失败的快照恰恰**可能带着违规内容**
——那份快照进库会被 `assertProjectLocks` 拒收（AC-6.4），连带整次写盘失败。
`video_url` 同样保留：上一次成功产出的成片是真实存在的产物，重试失败不该把它抹掉。
于是失败的语义是「最近一次尝试失败了」，而不是「这板没有东西」。

### 2. 写盘串行

整集生成会连着报 5 个终态，每次都是「读库 → 改一板 → 写回」。并发跑会互相盖掉：
后写的那份读到的是没有前一板结果的旧快照。写入器内部把写盘串成一条 promise 链，
`idle()` 等它跑干。这条串行化有专门用例守着（并发报到 5 个任务，五板结果都在）。

### 3. `patch`：草稿要跟上，但保存态不动

新增 `useProjectEditor.patch()`，收下「已经由别的通道落库」的值：更新草稿与 `draftRef`，
**不动** `dirtyRef` 与 `saveState`。

草稿必须跟上——否则用户随后的任意一次编辑都会把草稿里的旧值（`video_url: null`）
写回库里，把刚落库的成片地址盖掉。但它不是用户的改动，页面不该显示「未保存」。
若此刻本就是 `dirty`（用户正在输入），那份 `dirty` 也原样留着。

落库失败时反过来走 `update()`：置「未保存」，让防抖与手动保存去重试。
两条通道之间因此有个明确的降级方向，而不是一失败就没人管。

### 4. `withDrafts` 保留 `status`

生成期字段从两个变三个：`video_url` / `prompt_final` / `status` 一律取库里那份。
编辑态里的 `status` 是挂载快照，编辑区没有任何入口改它，拿它盖回去只会把
生成通道刚写下的 `generated` 退回 `filled`。

## 四、红线一条没放宽

| 红线 | 在新通道上仍然成立的理由 | 用例 |
| --- | --- | --- |
| `RULE-4` 单板 ≤ 30s | 拦截链在**入队之前**跑，超上限直接 `blocked`，不建任务也就没有终态可落 | 「超 30 秒的板压根不入队，也就没有任何东西落库」 |
| `RULE-9` / AC-6.4 衔接排除 | 落库仍走 `repository.save` → `normalizeProject` → `assertProjectLocks`，快照里带衔接手法一律拒收 | 「落库的 Prompt 快照里没有衔接手法」（写入器与编辑页各一条） |
| `RULE-2` / `RULE-3` 五节拍锁与宫格锁 | `applyJobResult` 经 `rebuildBeat` + `hydrateProject` 出口，锁跟着回来 | 「回写不破坏五节拍锁与宫格锁」 |

另有一条接线契约：注入 `queue` 又给控制器传 `onSettle` 直接抛错。
挂点只能有一处，否则「到底谁在写库」这件事会随调用方而变。

**没有删除或放宽任何既有用例**，包括 W3 那两条「生成成功后点保存即落库」——
它们走的是编辑页的手动保存路径，与新通道并存，仍然全绿。

三条断言值得单独说，因为它们是这次的验收点：

1. **「点完生成就离页」**用 `fireEvent.click` 之后一个微任务都不让出去就 `unmount()`,
   任务还停在「生成中」页面就没了。这条断言只能由挂在状态机上的通道满足——
   把 `onSettle` 摘掉（只留补写 effect）它立刻变红，验证过。
2. **「控制器先 dispose 再收尾」**在写入器层面把同一件事钉得更死：可控传输层
   保证任务一定在 `dispose()` 之后才返回，`dispose` 那一刻断言库里还是 `null`。
3. **「生成之后再编辑一次并保存」**守的是第 4 个决策：改剧情核心并保存之后，
   `video_url` 与 `generated` 都还在。

新增的 3 条编辑页用例在改动前的 `EditorPage.tsx` 上全部失败（逐条跑过）。

## 七、遗留缺口

W3 §六的缺口 1 关闭，其余原样顺延（成片页只有已生成 / 未生成、参考图只在内存、
整集时长偏差只提示不阻断、项目级字段没有编辑入口、迁移链是空表、
控制器换项目靠断言）。本槽位新增两条：

1. **生成任务表仍是 localStorage，且与项目库不同源。** 任务表被清或换了浏览器，
   历史生成记录（attempt / 失败原因）就没了；项目里只剩最终的
   `video_url` / `status`。要留生成历史得把任务表也放进 IndexedDB 的一张表。
2. **写盘失败只降级到编辑态通道，没有可见提示。** 落库失败时页面变成「未保存」,
   用户看到的是一个"自己没改却未保存"的状态；顶部栏没有说明这是生成结果没写进去。
   补一句提示需要先定文案位置，归到成片页 / 生成状态呈现那一档一起做。
3. **在途状态不落库。** 「生成中」是视图状态，只活在内存的任务表里。
   离页再回来看到的是最近一次终态，而不是"仍在生成"——目前没有轮询与恢复机制，
   接真实接口（异步出片）时需要按任务 id 回查上游，那时才有必要落在途状态。
