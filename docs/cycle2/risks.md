# Cycle 2 风险台账（Risks）

- 文档编号：`ARCH-C2-RISKS`
- 槽位：**Wave 6 / 80 · Cycle 2 架构波 · PLAN SLOT W6**
- 配套：[`architecture-delta.md`](./architecture-delta.md)、[`ready-queue.md`](./ready-queue.md)、[`DISPATCH.md`](./DISPATCH.md)

## 0. 台账口径

每条风险固定五段：**现象（可验证的事实）→ 为什么危险 → 触发条件 → 处置 → 判据**。

- **现象**必须是实测事实，不是判断。判断写在「为什么危险」里。
- **判据**必须是「谁在什么时候能看出这条风险已被消掉」，不是「我们会注意」。
  没有判据的风险条目等于备忘录，两轮后就没人读了。

风险等级：`R-高`（会丢数据或让红线失效）、`R-中`（会让成本非线性增长）、`R-低`（会让口径漂移）。

| # | 风险 | 等级 | 处置槽位 |
| --- | --- | --- | --- |
| 1 | `纯硬切` canon：代码目录比法源多一项 | **R-高** | `W9-I1`（阻塞于法源裁定） |
| 2 | 分支分叉（branch fragmentation） | **R-高** | `W7-I1` |
| 3 | `SCHEMA_VERSION` 迁移：框架在位但从未执行 | **R-高** | `W9-I4`；规约见 §3.5 |
| 4 | 生成任务表在封套之外 | R-中 | `W8-I1` |
| 5 | Cycle 1 验证波从未召开 | R-中 | `W10`（分开记账） |
| 6 | 「先加个 Key 跑通」的诱惑 | R-中 | `W7-I4`（产物扫描） |

## 1. `纯硬切` canon —— 代码目录比法源多一项

### 现象

三处口径实测不一致：

| 位置 | `纯硬切` 的状态 |
| --- | --- |
| `apps/web/src/domain/transitions.ts`（`8ffe44f`） | **在**。`TRANSITION_CATALOG` 6 项，`HARD_CUT` / `纯硬切` 在列；`CANON_TRANSITION_BY_BEAT_INDEX[3] = '纯硬切'` |
| `docs/methodology/glossary.md` `METH-002 §5`（封闭枚举的**法源**） | **不在**。只列 5 项 |
| `docs/methodology/golden-5-beats.md` `METH-003 §1/§8`（要求它的地方） | **要求**。B3 → B4 基准衔接就是「纯硬切」 |

即：**方法论文档内部自相矛盾**（`§5` 的枚举容不下 `§8` 的基准值），
代码选了跟 `§8` 走，于是代码比 `§5` 多一项。

这个差异**至少从 W1 起就存在**且被独立发现过两次：
`docs/DISPATCH.md` 的 P2 小节记为 `O-P2-1`（处置口径「PRD 不自行扩枚举，模板暂存字面值并标记
`pending_canon`」），`cursor/w3-templates-golden-library-e98c` 的 §4 把差异做成了数据
（目录项新增 `canon_source` / `pending_canon` / `pending_canon_reason`，配 `PENDING_CANON_TRANSITIONS`
待批清单与 `isPendingCanonTransition()`）。

**但那条分支还没合流**（见 §2）。所以此刻在最好的应用分支上，
这个差异**没有任何标记**——它只是静静地存在于 `transitions.ts` 里。

### 为什么危险

不是「少了一个词」。危险在于**衔接枚举是封闭的，而封闭是一条红线的实现手段**。

`RULE-12` / `AC-R2-1` 要求组间衔接人工设定**且枚举封闭**；`transitions.ts` 的文件头把这条
写成了纪律：「枚举封闭：新增取值必须先改方法论法源，再改本文件」。
而实际发生的事情正好相反——**先改了本文件，法源没改**。

于是「封闭」这个词失去了可验证的含义：问「这个取值合法吗」，答案取决于你查代码还是查法源。
一旦这种情况被默认接受，下一个槽位加第 7 个取值时就没有任何机制能拦住它——
拦它的规矩已经被破过一次，且没有人记账。

具体的下游损害已经开始扩散：

- `store/projectFactory.ts` 的预置衔接（W3 修过一次：store 槽位原来预置自由文本
  `'卡点硬切 + BGM 升调'`，不在封闭枚举内，落库会被 `RULE-9` 拒绝）；
- 飞书导出（`share/**`）与成片页衔接总表会把 `纯硬切` 输出给用户，
  而 PRD `AC-F5-9` 要求「待法源确认」的取值必须**标注**——现在没有标注，因为代码不知道它待确认；
- 模板库 B3 用的就是这个值。

### 触发条件

- **裁定为「改基准值」（移除 `HARD_CUT`）**：库里已有项目的 B3 衔接值变成非法值，
  读回时 `normalizeProject` → `RULE-9` 拒绝 → **该项目整个读不出来**。
  这需要一次真正的 `SCHEMA_VERSION` 迁移（见 §3），而迁移链现在是空表。
- **裁定为「补入枚举」**：无数据风险，只需清标记。
- **不裁定**：差异继续存在，且随着 `export/**`、`share/**`、`domain/templates.ts` 合流，
  依赖这个值的模块从 1 个变成 4 个。

### 处置

1. **立刻（`W7-I1`，M2）**：合 templates 分支时取并集，让 `pending_canon` 标记进入主干。
   这一步不解决矛盾，但**让矛盾变成数据**——从「没人记得」变成「查数据就能看到」。
   合并判据：`纯硬切` 仍通过 `isTransitionRule`，B3 衔接值不变（**待批 ≠ 不可用**）。
2. **W8-I2**：飞书导出与成片页对 `pending_canon` 取值加「待法源确认」标注，兑现 `AC-F5-9`。
3. **W9-I1（需外部裁定）**：方法论槽位在 `METH-002 §5` 二选一。
   实现侧两条路径都已写好（[`ready-queue.md`](./ready-queue.md) §3 `W9-I1`）。
4. **降级方案**：裁定未达则保留现状并顺延，在 [`DISPATCH.md`](./DISPATCH.md) 记明
   「顺延原因＝外部裁定未达」。**实现槽不得自行裁定法源**——自行裁定正是这条风险的成因。

### 判据

**这条风险消掉的标志只有一个**：存在一条测试，断言
`TRANSITION_CATALOG` 的取值集合与 `METH-002 §5` 的枚举集合**完全相等**。

在那条测试存在之前，无论文档写得多清楚，漂移都可以在下一次提交里静默发生。
`pending_canon` 是**记账**，不是**修复**——它让漂移可见，不阻止漂移。
这个区别要说清楚，否则会有人以为合了 templates 分支这条风险就关闭了。

## 2. 分支分叉（branch fragmentation）

### 现象

远端 20 条分支，**5 条含未合流的实现成果**，分布在 **3 个不同的 merge-base** 上：

| 分支 | HEAD | merge-base | 与 `8ffe44f` 的冲突文件数（实测） | 代码量 |
| --- | --- | --- | --- | --- |
| `cursor/wave2-w2-export-ca31` | `c92ce40` | `a8f6f26` | — | 2451 行（**被 925d 完全包含**） |
| `cursor/w4-feishu-export-925d` | `82f4845` | `a8f6f26` | 1 | 4528 行 |
| `cursor/w3-templates-golden-library-e98c` | `21ae263` | `a8f6f26` | 2 | 1356 行 |
| `cursor/w4-a11y-6861` | `d24127d` | `a3aed39` | 2 | 946 行 |
| `cursor/w4-image-store-8321` | `3d4b5af` | `6a118af` | 3 | 2813 行 |

合计约 **9600 行**已完成且已自测通过的代码，**一行都不在最好的应用分支上**。

文本冲突总数只有 **8 个文件**——低得出乎意料。但这个数字会骗人：

**真正的成本是语义断裂，而它不体现在冲突数里。** 实测两处：

1. `w4-image-store-8321` 写在**已被取代的领域模型**上（merge-base `6a118af` 用 WK1 的
   `gridSizeForBeat` / `GridSize` / `GridCell`；W3 已整体换成 WK2 的
   `frameCountFor` / `FrameCount` / `BeatFrame`）。Git 判这些文件「干净」，因为
   W3 没碰过 `adapters/images/**`——它们是新文件。断裂只有 `typecheck` 会报。
2. `w4-feishu-export-925d` 的成片页路由壳读 `findDemoProject`（`data/demoProjects`），
   而 W3 已按派单**删除**了该演示夹具。合并后 import 指向不存在的模块。

### 为什么危险

**合并成本随时间超线性增长，而且增长是不可见的。**

分支分叉的代价不是「以后要合一次」，而是三件同时发生的事：

1. **重复劳动已经发生过一次。** `wave2-w2-export-ca31` 与 `w4-feishu-export-925d`
   两个槽位都产出了完整的 `export/**`（2451 行）。925d 恰好是 ca31 的线性后继，
   所以这次没白干；**但那是运气**——如果两个槽位各自从 `a8f6f26` 起写成片页，
   就会有 2400 行的双份实现和一场无法机械解决的冲突。
2. **旧模型上的工作在持续贬值。** image-store 的 2813 行写在 W3 已经废弃的字段名上。
   本次运气也不错（耦合面只有 `frameImageKey.ts` 一个符号，因为图片坐标只需要
   「这块板有几格」这一个事实）。但这是**该模块设计得好**的结果，不是分叉这件事无害。
3. **每条分支各自的测试都是绿的，合起来没人验证过。** 例如 `styles.css`：
   a11y（+66 行）与 image-store（+92 行）都改它，实测两者与 `8ffe44f` 各自不冲突
   （改的是不同区段），但**两者互相之间从未被一起构建过一次**。
   `BeatBoard.test.tsx` 同理：W3 改过它的数据源，a11y 改过它的断言，Git 判干净。

第 3 点是最容易被低估的：**「各自绿」不蕴含「合起来绿」**，
而分叉时间越长，这类未验证的组合数越多（组合数随分支数平方增长，不是线性）。

### 触发条件

- 再有一个槽位从旧 merge-base 起分支 → 第 4 个 merge-base，组合面继续扩大；
- `domain/**` 再发生一次模型级重构 → 未合流分支的贬值从「一个符号」变成「整个模块」；
- 分叉持续到 W10 → 验证波要在一条**没人验证过的合流结果**上跑集成测试，
  验证波会变成「集成 + 补合并缺陷」，而验证波按硬规则**只修不加**，
  一旦要动结构就整波作废。

### 处置

1. **`W7-I1` 一次合完，四次合并顺序固定 M1→M4**
   （[`architecture-delta.md`](./architecture-delta.md) §3.2）。
   排序依据：先合语义断裂需要人工重定向的，后合纯附加的；`styles.css` 的两个改动者相邻。
2. **不单独合 `ca31`。** 合它等于制造一次库存里本来不存在的冲突（两侧都改
   `ExportView.tsx`）。这是本波最直接的一条成本节省。
3. **每次合并后四闸门全绿才进下一次**，且逐文件用例数 ≥ 两侧最高值。
   **任一文件的用例数低于两侧最高值 = 有测试被删，立刻回退。**
4. **停在中途也是可交付状态。** 顺序设计成 M1→M4 就是为此：某次合并转绿成本失控时，
   停在那一次、记账、顺延，不放宽闸门。

### 判据

- **短期**：`W7-I1` 交付后，`git branch -r` 里不存在含未合流实现成果的分支
  （文档分支不计）。这是可机械核查的。
- **长期（更重要）**：新槽位开分支时的 merge-base **必须是当前最好的应用分支**。
  这条要写进派单模板。分叉不是一次性事故，是一种会复发的工作方式——
  本波合完这 5 条，下一轮若仍从旧基线开分支，同样的账会再记一遍。

## 3. `SCHEMA_VERSION` 迁移 —— 框架在位但从未执行

### 现象

四条实测事实：

1. `SCHEMA_VERSION = 1`（`adapters/persistence/schema.ts`）；
2. `MIGRATIONS = {}`（`adapters/persistence/envelope.ts`）——**空表**；
3. 迁移机制本身写得相当完备：`readVersion` 拒绝非法版本、拒绝高于当前程序的版本，
   `migrate()` 缺条目时抛 `ArchiveFormatError('缺少 vN → vN+1 的迁移函数，拒绝静默丢数据')`，
   迁移后统一过 `normalizeProject`（结构锁）；
4. **这条链从未被真正跑过一次。** 空表意味着 `while (version < SCHEMA_VERSION)`
   的循环体从未执行；「缺口检测」分支也没有对应的迁移条目去触发。

W3 自己把这条记成了遗留缺口第 6 条，并写明理由：
「本槽位改了落库字段名（camelCase → snake_case），但 store 槽位从未发布，
库里不存在旧格式数据，所以没有补 v1 → v2。**下一次改落库结构必须同时 +1 版本号并补迁移函数**。」

这个推理**在当时是正确的**。风险在于它的有效期。

### 为什么危险

**「从未发布过，所以不需要迁移」是一个会静默失效的前提。**

它失效的那一刻没有任何信号：没有编译错误、没有测试失败、没有告警。
第一个真实用户在浏览器里存下一个项目，这个前提就不再成立了——
而代码里没有任何东西记录「这个前提曾经被依赖过」。

三个具体的危险面：

**(a) 空表把「缺口检测」这条防线变成了未经测试的代码。**
`migrate()` 里那句「拒绝静默丢数据」是整个持久化层最重要的一行防御。
它现在**从未被执行过**。第一次执行它的时候，就是第一个用户升级的时候——
那不是验证代码路径的好时机。

**(b) 两个版本号，语义不同，改错一个就是数据事故。**
Cycle 2 会引入第二个版本号（`w4-image-store-8321` 把 IndexedDB 的 `DB_VERSION` 升到 2）：

| | `DB_VERSION` | `SCHEMA_VERSION` |
| --- | --- | --- |
| 管 | 物理布局（有哪些 object store / 索引） | 记录的字段结构 |
| 读它的是 | 浏览器 `onupgradeneeded` | `envelope.ts` 迁移链 |
| 跨设备可见 | 否 | **是**（备份文件带着它走） |
| 加图片仓 | +1（1 → 2） | **不变** |

危险的具体形态：有人加了个落库字段，看到 `DB_VERSION = 2` 就以为「版本号已经是 2 了」，
不补 `SCHEMA_VERSION`。于是老备份读回来缺字段，而**迁移链根本不会被调用**
（`version === SCHEMA_VERSION`，循环不进入），结构锁也拦不住——
缺一个可选字段不违反任何锁。数据就这么静默地半损坏了。

反向同样危险：改 `SCHEMA_VERSION` 却不动 `DB_VERSION`，新字段的索引不存在，
查询静默走全表扫描。

**(c) 本 Cycle 有一条真实的迁移触发路径。**
若 §1 的法源裁定走「改基准值」（移除 `HARD_CUT`），库里所有项目的 B3 衔接值变成非法，
`normalizeProject` 会拒绝**整个项目**。这是本 Cycle 唯一一条会真正需要 v1 → v2 的路径，
而它同时也是第一次执行迁移链——**第一次执行就承载真实数据改写**，风险叠加。

### 触发条件

| 触发 | 后果 |
| --- | --- |
| 任何落库字段增删改名而不 +1 | 老数据静默半损坏，无告警 |
| §1 裁定走「改基准值」 | 需要真实的 v1 → v2 数据改写；迁移链首次执行 |
| 混淆两个版本号 | 见 (b) 的两个方向 |
| 产品发布后才发现前提失效 | 用户库读不回来；此时补迁移必须**先猜出**那些库长什么样 |

### 处置

1. **规约 C2-DB-1**（[`architecture-delta.md`](./architecture-delta.md) §2.1）：
   `DB_VERSION` 与 object store 清单只允许在 `adapters/indexeddb/beatboardDb.ts` 声明，
   禁止任何驱动自行 `factory.open()`。理由是 IndexedDB 版本号是**库级**的：
   两处开库必然 `VersionError` 或把连接卡在 `blocked`。
2. **规约 C2-DB-2**：改 `DB_VERSION` 不得顺手改 `SCHEMA_VERSION`，反之亦然；
   两者同时改的提交必须分别说明理由。
3. **本波裁定：Cycle 2 结束时 `SCHEMA_VERSION` 应仍为 1。**
   这不是拖延，是主动的结构选择——`Frame.reference_image_key` **不进落库结构**
   （[`architecture-delta.md`](./architecture-delta.md) §2.3），图片坐标全部可从项目结构推导，
   所以加图片仓不改记录字段。备份的参考图清单是纯附加信息（缺失按 0 处理），也不触发 +1。
4. **`W9-I4` 做迁移链演练**：在空表前提下构造一个**假的** v1 → v2 迁移跑通全链
   （写 v1 备份 → 注册假迁移 → 读回 → 过锁），并覆盖「缺口检测」与「版本高于当前程序则拒绝」
   两条既有分支。目的就是**让那句「拒绝静默丢数据」在真实用户之前先被执行一次**。
5. **两个版本号的语义区分写成测试**：改 `DB_VERSION` 不影响封套版本，反之亦然。

### 判据

三条同时成立才算这条风险降到可接受：

1. `MIGRATIONS` 的**缺口检测分支有测试覆盖**（不是有代码，是有测试执行过它）；
2. 存在一条测试同时断言两个版本号的独立性；
3. `schema.ts` 与 `beatboardDb.ts` 的文件头各有一段**指向对方**的说明，
   写明「另一个版本号管什么、什么时候该动它」。

第 3 条看起来最软，但它是唯一能在**编辑那个文件的当下**起作用的措施。
风险台账没人在改代码时读，文件头有人读。

## 4. 生成任务表在封套之外（R-中）

### 现象

项目在 IndexedDB（`beatboard` 库），生成任务表在 `localStorage`
（`GENERATE_JOBS_STORAGE_KEY = 'jiepaiban.generate.jobs.v1'`）。
`PersistedEnvelope` 只装 `projects`，**不含任务**。任务表自带一个第三个版本号——
键名里的 `.v1`，它既不是 `SCHEMA_VERSION` 也不是 `DB_VERSION`，且没有任何迁移机制。

### 为什么危险

在 [`architecture-delta.md`](./architecture-delta.md) §1 的 sink 落地**之前**，
任务表是 `video_url` 的**唯一**持有者之一（成功但未落库的那段窗口）。
两个介质不同寿：清理站点数据、隐私模式配额回收、浏览器配置差异都会让两边不同步。
导出备份换机导入后，任务表为空——若那时项目记录里还没有 `video_url`，成片地址就没了。

sink 落地后风险显著下降（`video_url` 的事实源变成项目记录），但不为零：
失败原因与重试语义仍只在任务表里，导出备份不含它们。

### 触发条件

用户导出备份 → 换机导入 → 打开成片页。sink 之前：成片地址可能已丢失。
sink 之后：成片地址在，但「上次为什么失败」不在。

### 处置

1. `W7-I2`：sink 让 `video_url` 的事实源变成项目记录；
   `controller.stateOf` 取值优先级固定为**项目记录 > 任务表**，
   使「库里已生成、任务表被清」的用户看到「已生成」而非「未生成」。
2. `W8-I1`：启动对账（[`architecture-delta.md`](./architecture-delta.md) §1.4）处理两边不一致的五种情形。
3. **本 Cycle 不把任务表并入封套。** 任务是运行期状态，不是用户资产；
   并进封套会让备份文件带上一堆 `remote_task_id` 这类换机后无意义的字段。
   若将来要并入，`.v1` 这个隐式版本号必须先并入 `SCHEMA_VERSION` 体系——
   记在此处以免届时被漏掉。

### 判据

存在一条测试：清空 `localStorage`（模拟任务表丢失）后，
已生成项目的成片页仍显示「已生成」，且板级动作可用（能重新生成）。

## 5. Cycle 1 验证波从未召开（R-中）

### 现象

远端 20 条分支中没有任何 W5 槽位分支，`docs/` 下没有 Cycle 1 验收报告。

### 为什么危险

`wave-plan.md` §0.1 第 2 条写明：验证波结束时 `verify` 必须全绿，
**否则该 Cycle 不算完成，缺口顺延进下一 Cycle 的架构波重排**。
本波就是执行这条规则的地方。

危险不在于「少跑了一轮测试」，而在于**单测与集成闸门守的不是同一件事**。
L7（所见即所发）要求面板 DOM 文本与 `assemble()` 输出逐字符相等——
这条只有在真实 DOM 上比对才有意义，组件单测断言的是自己渲染的东西。
L4 全站扫描要求遍历三条路由的 DOM 文本与路由表，这也不是任何单测的覆盖面。

更实际的问题：**这类债不记账就会消失。** 两轮之后，

2. **W10 两笔债分开记账**（[`ready-queue.md`](./ready-queue.md) §4 的表）。
3. Cycle 1 的部分欠项在本 Cycle 提前还：迁移演练 → `W9-I4`；
   性能基线 → `W9-I4`。这两项不必等 W10，且它们本来就需要在结构改动**之前**有基线。

## 6. 「先加个 Key 跑通」的诱惑（R-中）

### 现象

`adapter.ts` 的文件头已经写明「不发真实网络请求，不读任何 API Key / 环境变量」，
`FORBIDDEN_SUBMISSION_KEYS` 也把 `api_key` / `apiKey` / `token` / `secret` 写成了可测断言。

**但这些守卫都只覆盖「提交体的键名」和「文档里的承诺」。**
没有任何机制阻止某个槽位在 `main.tsx` 或 `.env` 里加一个 `VITE_SEEDANCE_API_KEY`
然后在传输层拼一个 `Authorization` 头。而这么做在 Cycle 5 真连时会非常有诱惑力——
它是让真连「今天就能跑」的最短路径。

### 为什么危险

Vite 的 `VITE_` 前缀变量**会被编译进客户端 bundle**。
这不是「配置不当」，是**不可逆的泄漏**：构建产物在谁手里都能读，
CDN 上、用户浏览器缓存里、任何一份 `dist/` 拷贝里。
密钥一旦进过一次构建，就必须轮换——而通常发现的时候已经过了很多次构建。

PRD NFR 的「Key 不落客户端」被排在 Cycle 13（最小代理服务端）。
Cycle 5 要真连、Cycle 13 才有代理，这中间有 8 个 Cycle 的窗口期，
**诱惑正好落在这个窗口里**。

### 触发条件

Cycle 5 的真连槽位想「先跑通再说」。或者更早——任何人想在本地验证一下端点。

### 处置

1. **类型层让它没地方放**：`SeedanceEndpointConfig` 只有 `baseUrl` / `timeoutMs` / `maxPollMs`，
   **没有 `apiKey` 字段、没有 `token` 字段、没有 `Authorization` 头的拼装点**
   （[`architecture-delta.md`](./architecture-delta.md) §4.3 约束 2）。
2. **适配器不读环境变量**：`generate/**`、`domain/**`、`adapters/**` 内
   `import.meta.env` / `process.env` 零命中，CI 扫描（`W7-I4`）。
   唯一的环境读取点是应用组装根。
3. **`baseUrl` 为空则回落桩件**，本地开发与全部测试照常跑——
   把「不配置」做成一个完全可用的状态，才能让「不配置」成为默认选择。
4. **产物扫描**（`W7-I4`）：`build` 之后扫 `dist/**` 的 `sk-` / `api_key` / `apiKey` /
   `secret` / `authorization` 等模式。**这是唯一能兜住「某人图省事」的闸门**——
   它检查的是产物，不是意图。前三条都可以被绕过（改类型、改扫描白名单），
   产物扫描要绕过必须显式改 CI，而那是一个会被 review 看到的动作。
5. **口径写明**：在代理服务端存在之前，真连**本就不该可用**。这不是把问题推给未来，
   这是正确的产品状态。

### 判据

CI 中存在产物扫描且有反例测试（植入含密钥模式的临时文件 → CI 失败）。
**判据是反例测试，不是「扫描已接入」**——没有反例测试的扫描器，
在正则写错时会永远静默通过，而那种失效方式无法被发现。
